# Cooperative coupled-solver design and feasibility checkpoint

Recommend a separate experimental **single persistent block, point-wise evaluation** prototype on top of the explicitly selected tangent-cache owner. Its only parallel numerical operation should initially be `evaluate_coupled`'s independent per-point disk residual and two Jacobian rows. Keep the normal pressure/mask solve, dP/dx assembly, scalar reductions, complete-pivot factorization, Newton/halving decisions, patch order, point impulse application and publication serial and unchanged. No replacement, capability probe, automatic selector or GPU execution was implemented in this checkpoint.

## Evidence and the first operation

The current tangent-cache solve is launched at grid=1/block=1 (`cached_tangent_response.mojo:90`). Historical CUDA/NVTX captures measured its velocity kernel at 1090.370880 ms, roughly 98.84% of GPU kernel time on the difficult three-body/two-patch/eight-point target. The original-to-invariant gain was materially larger than the latest tangent reuse gain. Balanced host/API interleaving measured tangent versus invariant -38.5154 ms / -3.36% on that target and -28.1429 ms / -37.67% on centered rebound. These are measurements of existing modes, not cooperative speedup predictions. See `../physics-tangent-reuse/RESULTS.md` and `../physics-owner-assessment/measured.json`.

Target logical work is still 96 velocity sweeps, 192 patch attempts, 505 Newton corrections/linear solves, 2707 evaluations and 1853 halving trials. Existing profiling does **not** time individual evaluation, mask, disk or linear-factorization routines. A register count of 255 in the earlier serial capture does not establish spills or explain the bottleneck. GPU FP64 arithmetic throughput, dependent instruction latency, barriers and resource pressure remain unmeasured for the proposed design.

After pressure and dP/dx are fixed, point i reads immutable nn/NT/TT/pressure/qt/x/dP data and writes only residual[2i:2i+2] and Jacobian rows 2i,2i+1. It never reads another point's residual/Jacobian output. Each lane retains the original increasing-k/increasing-j loops and exact expression grouping. `disk_min` retains its unconstrained test, bracket, 64 dependent bisections and final shifted solve (`friction_kernels.mojo:25-35`). Bisection iterations inside one root cannot run in parallel. The derivative depends on that same point's completed root. Trial evaluations without a Jacobian still benefit from distributing point disk roots; parallelizing Jacobian columns alone would miss much of the 2707-evaluation schedule.

At count=4 this offers at most four independent point tasks, not 32 useful root tasks. At count=1 it has no root parallelism and can be slower. Different stick/slide/zero-radius branches can serialize within the warp and limit gains. An 8x8 Jacobian has 64 independent final elements once point derivatives/dP exist, but distributing columns is a later alternative that adds communication and duplicates or shares point temporaries. Do not combine it into the first prototype. Parallel normal-mask candidates, terminal residual checks or factorization are also deferred.

## Persistent block versus many launches

Use one ordinary kernel launch with one block of 32 threads as the first declared configuration. Lane 0 controls the existing bounded sweep/patch/Newton/halving loops. Lanes 0..count-1 evaluate their own point during an announced evaluation phase; other lanes wait at the same phase barriers. Lane 0 also owns point 0. This is a block that persists for the current solve, not a background service, dynamic work queue, cooperative grid launch or inter-block global barrier. Exactly one existing velocity launch would be replaced in a future isolated opt-in owner; surrounding preparation, validation and commit stay intact.

Conceptual phase sequence:

1. Leader prepares the current immutable evaluation inputs and original pressure/dP result, then publishes a phase command.
2. All lanes rendezvous. If the shared command permits evaluation, each active point lane computes its original scalar program into disjoint scratch; inactive lanes produce no point output.
3. All lanes rendezvous. Leader reads point results in increasing point order, reconstructs the original evaluation, computes the original ordered norm/rank/acceptance decision and updates controller state.
4. All lanes rendezvous before scratch reuse or a new command. Termination/rejection is broadcast; every lane leaves the same loop together.

Every evaluation needs publication, completion and safe-reuse ordering. Do not assume warp lockstep or replace barriers with volatile reads. Do not put a full-block barrier inside `lane<count`, return from one point lane on invalid input, or break a loop only on the leader. All conditional exits become shared phase decisions; idle lanes participate until uniform exit. Normal/fallback/error paths must follow the same synchronization discipline.

Launching a helper kernel for each evaluation would add roughly 2707 launches on the current target, store/reload iteration state and require ordered follow-up decisions. Existing 18-launch total/API launch cost around 0.039 ms describes the current schedule and cannot be multiplied into a reliable new-launch cost prediction. Host decisions would introduce waits; device-launched children need additional capability and ordering proof. CUDA graphs still require expressing dependent decisions and do not remove numerical sequencing. Per-evaluation launches are useful only as an isolated correctness oracle/microbenchmark, not the recommended integrated prototype.

## Memory, races and exact rejection behavior

Use a fixed per-block evaluation scratch budget, declared before code is written. A conservative layout contains nn16+NT32+TT64+operators256+qn4+qt8+x8+q4+pressure4+dP32 = 428 Float64 input/work words; assembled residual8+Jacobian64 = 72 Float64 output words. These total 4000 bytes. Reserve eight additional Float64 canary words (64 bytes) and at most 128 bytes for counts/commands/stages/validity/ownership flags: **4192 bytes maximum explicit block scratch** for this layout. Any lane-private arrays, compiler spills, scalar rank workspace or host owner buffers are additional and must be reported separately. No full 16-patch table is needed in shared scratch. Reuse it for one evaluation/patch at a time; clear padding/output deterministically before each use. Original global resolve-local cache/canaries remain unchanged.

The exact pinned MAX address-space/barrier APIs are an unresolved implementation gate. Repository GPU kernels use `max.gpu` thread indices and already qualified `DeviceContext.enqueue_function`, but contain no block-shared scratch/barrier witness. The installed std/MAX libraries are packaged `.mojoc` files rather than readable GPU source. The official Mojo allocation reference documents address-space selection, but its displayed version is 1.1.0 and does not prove the pinned MAX barrier signature. GPU-specific official URL lookups were inaccessible. Do not infer compatibility or upgrade anything; the eventual prototype must first demonstrate these primitives on the pinned versions. No tiny GPU check was needed for this design-only conclusion. If shared allocation cannot be expressed, a disjoint global scratch plus a verified block barrier can be assessed explicitly, without silently claiming shared-memory performance.

CUDA's primary documentation establishes block-scoped shared scratch and synchronization between producers and consumers. Shared memory belongs to a block; it does not synchronize separate blocks. Source-independent design risks include overlap/incorrect strides, stale padding between count4/count1 or Jacobian/nojacobian phases, a producer overwriting scratch before its consumer is done, divergent exits, replicated leader body stores, and leader register pressure. One writer per output word and one writer for commands/body/work/status avoid atomics. Do not have workers increment shared work counters or mutate body state. Keep the existing candidate transaction private until its existing validated commit. [NVIDIA SIMT kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)

`evaluate_coupled` can return early with partially populated arrays. Bit equality must include that observable result, not just `valid=False`. Workers therefore record point-local completion stage and validity; the leader assembles only the ascending prefix the original routine would have reached. A disk failure leaves that point's residual/rows zero; a derivative failure can occur after its residual was written. Prior completed rows/residuals survive, later outputs remain zero. Pressure/mask failures occur before worker work and broadcast a uniform skip. Concurrent lanes may perform extra bounded, unconsumed point arithmetic after an earlier point would fail; this must be disclosed and cannot count as another logical evaluation/Newton/halving trial. No speculative future line-search trial or iteration is allowed. If all original partial-output/invalid cases cannot be preserved safely, stop instead of accepting only successful-case equality.

## Precision and bit identity

Bit-identical outputs are a credible **acceptance target**, not established capability. Each scalar output can retain the identical Float64 operations in the identical per-output order even when different outputs run concurrently. Binary64 scratch stores do not intentionally reduce precision. Keep leader reductions in original order, strict mask/pivot comparisons and first-on-tie behavior, complete-pivot 256eps cutoff and least-norm/null-space operations, and the exact first accepted halving decision. Retain original Float64 division/sqrt and expression grouping; no FP32, tensor/matrix math, fast-math flags, tree reductions or atomically accumulated sums.

Compilation context can alter contraction/reassociation, spilling or scalar instruction selection. Float64 alone is insufficient proof: fusion and reduction order affect rounding. Inspect available generated device code and compare staged bit patterns on the same pinned GPU/toolchain. Do not change the reference compiler options or promise bit equality across architectures/compiler releases. Signed zero, subnormals/nonfinite handling, invalid partial arrays and all padded words need explicit comparison. One-bit differences can change rank/mask/acceptance and invalidate the optimization. [NVIDIA floating-point guidance](https://docs.nvidia.com/cuda/floating-point/index.html) · [Official Mojo allocation reference, version caveat above](https://mojolang.org/docs/std/memory/stack_allocation/stack_allocation/)

## One connected problem versus independent islands

The current difficult target's floor/lower and lower/upper patches share the lower dynamic body. Applying one patch changes the next patch's velocity inputs. Preserve their canonical serial order and the outer sweeps. Centered two-body rebound is one four-point patch, hence also one connected problem. Independent-island concurrency supplies no extra independent problem inside either target; any gain here must come from inner cooperative work.

One block can improve inner latency while using only a small part of the GPU. Its serial pressure/rank/control portion and four-point width bound acceleration. If f is the unmeasured fraction eligible for four-way parallel work, an optimistic upper bound before synchronization/divergence costs is 1/((1-f)+f/4); no numeric speedup follows without measuring f. Many genuinely independent islands could eventually occupy different blocks and improve throughput, but require a separate disjoint-dynamic-body proof, read-only static anchors, canonical local order, deterministic global reports/energy reduction and all-or-nothing publication. Existing serial island construction is a correctness baseline, not a qualified parallel solver. No multi-island scheduling is included in this prototype.

For gate1 the pure evaluator tests must cover count1..4 and error-stage combinations; a deterministic fixture corpus is required, not a new random search campaign. Existing trajectory/profile inputs are useful seeds, but current saved traces do not include all intermediate x/dP/disk stages. A future untimed reference instrumentation build must capture a small corpus or emit comparisons at every evaluation for the bounded qualified target, separately from timing. Capture at most one reset target invocation and a fixed small analytic witness set initially; store full binary64 input/output bits and first-difference indices. Do not infer isolated-input coverage from end-state equality.

For gate4 first prove clock-disabled and timed records exact, then run source and fresh precompiled comparisons against final fingerprints. Existing Nsight Systems/CUDA-NVTX settings can measure kernel durations separately, preserving clock/cache/boost settings. No new profiler is required. Measure the whole velocity kernel and whole API as primary endpoints; an isolated repeated evaluator kernel can estimate local cost with an identical serial control and output checksum but cannot prove integrated benefit. Optional device-phase instrumentation belongs in a separate untimed/diagnostic binary and needs calibration for its own overhead; current captures cannot attribute f. Report scratch/global storage, launch count, barrier schedule, compiler resource metadata if available, and observed work divergence. No assumed fourfold gain or generic FP64 attribution.

Stop at the first equality/race/rollback/physical-gate failure, unsupported pinned primitive, timeout, memory-reserve breach or competing GPU job. Preserve failures; do not expand the point-task mapping, parallelize masks/factors, change budgets or install tooling to rescue the attempt. Predeclare the performance decision: do not advance beyond this prototype unless cooperative versus leader-only and versus current serial target both have >=10/12 faster paired samples and all four batch median deltas faster. This operational threshold is not statistical confidence. Mixed/regressive target results end the attempt after the fixed batch budget; cheap regressions are reported explicitly and keep modes opt-in. A local evaluator speedup with no whole-target gain also stops expansion. No broad autotuning or repeated timing until a favorable result.
